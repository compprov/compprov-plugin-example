- **Topological & Provenance Fraud (Lineage Disconnection / Context Substitution sub-pattern):** Score 65 — the reward checkpoint is computed from the *closing* balance while its own metadata asserts it reflects the *opening* balance basis, meaning the value that should feed the reward formula (the opening balance) is effectively displaced by a different computed quantity.

#### Anomaly Localization
- **i_1** (`Sender balance (opening)`, value=10000, meta `balanceBasis: opening`) — the root value that the reward output's own metadata claims to be based on.
- **op_1** (`subtract`, formula `a-b`) — consumes `i_1` and `i_2` to produce `o_4` = 7000 (opening minus transfer amount). This step itself is correct and unremarkable.
- **o_4** (`Sender balance (closing)`, value=7000, meta `balanceBasis: closing`) — explicitly and correctly labeled as the *closing* balance.
- **op_2** (`multiply`, formula `a*b`) — consumes `o_4` (closing balance) and `i_3` (reward rate=2) to produce `o_5` = 14000.
- **o_5** (`Sender checkpoint reward`, value=14000, meta `balanceBasis: opening`) — the terminal leaf output. Its descriptor explicitly states the reward basis is "opening", but its actual lineage (`op_2` ← `o_4`) proves it was computed from the *closing* balance, not from `i_1` (the actual opening-balance root) at all.

**Attack flow:** `i_1`(10000) and `i_2`(3000) flow into `op_1` to yield `o_4`=7000 (correctly tagged "closing"). `o_4` and `i_3`(2) flow into `op_2` to yield `o_5`=14000. The terminal node `o_5` is mislabeled with `balanceBasis: opening`, falsely implying the reward was computed as `i_1 * i_3` (10000*2=20000). The graph's own metadata on `i_1` and `o_4` gives the ground truth needed to detect the mismatch: the declared basis of the consumed operand (`closing`, from `o_4`) directly contradicts the declared basis of the result (`opening`, on `o_5`), with no transformation node reconciling the two labels.

#### Details
**Mechanism:** Type-level validation passes trivially — every operand and result is a `java.math.BigInteger`, and the arithmetic replays exactly (7000*2=14000) against its own inputs. A naive provenance check that only verifies type continuity and local recomputation sees nothing wrong. The violation only surfaces when the *business* metadata attached to each node is cross-referenced: `o_4` is unambiguously declared `closing`, yet it is consumed by `op_2` to produce a result (`o_5`) that declares itself `opening`. No explicit domain-transformation step (e.g., an operation that reconstitutes the opening balance, such as adding the transfer amount back) exists anywhere in the graph to justify this relabeling. Per the Semantic Cast invariant, a domain transition must be backed by arithmetic that actually performs the change — here there is no arithmetic connecting "closing" back to "opening"; the label simply flips.

This pattern also reads as a Topological Lineage Substitution: the natural, metadata-consistent computation for an "opening-basis" reward would be `i_1 * i_3` = 20000 using the actual opening-balance root `i_1`, which is never consumed for this purpose (it is only consumed by `op_1`). Instead, the downstream (closing) balance is substituted into the reward formula while the label is left (or restored) to "opening," masking the substitution.

**Consequence:** If the reward program is intended to credit holders based on their balance at the start of the period (opening balance), using the post-transfer closing balance instead silently understates the reward by 6,000 tokens per this transaction (14,000 reported vs. 20,000 that the declared basis implies) — a 30% shortfall. At minimum, the graph contains an unresolved, auditable contradiction between declared business context and actual computational lineage, which is sufficient for a material finding regardless of which direction (over- or under-crediting) the true intended basis turns out to be.
