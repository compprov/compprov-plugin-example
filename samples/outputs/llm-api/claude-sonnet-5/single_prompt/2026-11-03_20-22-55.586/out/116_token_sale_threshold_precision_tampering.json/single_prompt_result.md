#### Details (Precision and Scale Tampering)
The flaw is a classic lossy divide→multiply round-trip: `o_5 = i_1 / i_2` (integer division, truncating towards zero) followed by `o_8 = o_5 * i_2`. Mathematically this reconstructs only `floor(i_1/i_2) * i_2`, which can never recover the fractional remainder of `i_1` that is not an exact multiple of one ether. Because the subsequent excess computation (`o_8 − o_9`) and the final bonus-eligible amount (`o_11`) are built entirely from this already-truncated `o_8`, the fractional remainder of the payment (0.5 ETH here) is silently and permanently dropped from the bonus calculation — it never reappears in any other variable in the graph (there is no "remainder" or "fractional wei" node). Local replay of each operation (`op_1`, `op_4`, `op_6`, `op_7`) passes perfectly against its own inputs, so naive step-level validation shows no error; the defect is only visible when comparing the terminal result against the original full-precision input `i_1`, which is exactly the asset-conservation check required by the invariants. This is a textbook case of "forcibly reducing an intermediate value's scale before completing an aggregation, causing residual value leakage." Because this computation represents a generic "minimum purchase gate" logic that would execute identically for every buyer in the token sale, any buyer paying a non-whole-ether amount (e.g., 3.5, 2.3, 0.9 ETH) systematically loses the fractional portion from their bonus-eligible excess — a materially sized, structurally repeatable (per-transaction, scalable with buyer count) leakage, satisfying both the Materiality Override and Cyclic Scaling aggravating factors. The ceiling for a simple rounding-mode disagreement (max 1 unit at target scale) does not apply here, since the discrepancy is driven by truncation of an entire unit of the operand's natural resolution (ether), not a rounding-mode nuance — this is a precision/target-scale defect, not a rounding-convention artifact.
