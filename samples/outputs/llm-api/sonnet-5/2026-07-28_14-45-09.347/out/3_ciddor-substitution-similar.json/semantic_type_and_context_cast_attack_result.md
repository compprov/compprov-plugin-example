## Details

**Mechanism.** This is a textbook Semantic Type and Context Cast: two variables (`i_82` and `o_81`) share an identical technical type (`BigDecimal`) and an almost identical human-readable business label (\"refractive index of air, Ciddor/Birch-Downs\"), which is exactly what allows the substitution to pass casual review, schema validation, and even numeric plausibility checks — `i_82 = 1.0002718` is numerically close to `o_81 = 1.00027175...`, differing only in the 6th\u20137th significant figure. A reviewer skimming values would see \"n \u2248 1.00027\" in both places and assume continuity. But provenance and business context are entirely different: `o_81` is a *measurement-specific, environmentally-derived* quantity computed from the actual recorded temperature/pressure/humidity/CO\u2082 for this calibration run (with report-linked wavelength metadata), whereas `i_82` is a *context-free constant* with none of that traceability. The consuming operation (`op_48`) uses `i_82` under the implicit assumption that it represents the true, adjusted-for-conditions refractive index — exactly the \"consumed as though already adjusted\" pattern called out in the attack definition — while the real adjusted value is silently discarded (confirmed by its leaf status).

**Why it survives casual/automated checks.** Mathematical replay of every operation is internally consistent (each op's inputs \u2192 output are arithmetically correct given `i_1`'s MathContext), so a naive recomputation check passes. Type checking passes (`BigDecimal -> BigDecimal` throughout). Exact-string duplicate-name detection would not flag this either, since `i_82`'s name (\"Ciddor / Birch-Downs. Refractive index of air, n.\") is a close paraphrase rather than an exact duplicate of `o_81`'s name (\"n: refractive index of air (Ciddor / Birch-Downs)\"), deliberately evading naive exact-match heuristics while preserving the illusion of business-meaning continuity to a human reader.
