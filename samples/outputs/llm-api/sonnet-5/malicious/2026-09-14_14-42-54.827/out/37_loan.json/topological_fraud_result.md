## Anomaly Localization

**Implicated nodes:** `i_4` (Extra principal prepayment, 5000.00, explicitly labeled "non-interest-bearing"), `i_3` (monthly rate), `op_13` → `o_21` ("Interest on prepayment [Month 4]" = i_4 × i_3 = 20.00000), `op_14` → `o_22` ("Prepayment principal portion [Month 4]" = i_4 − o_21 = 4980.00000), `op_15` → `o_23` (balance after prepayment), `op_22` → `o_33` ("Total interest accrued", terminal output).

**Flow of the defect:**
1. `op_13` computes `o_21 = i_4 * i_3 = 20.00`, a genuine interest component accrued on the extra principal prepayment in Month 4.
2. `op_14` immediately nets this interest amount *out of* the prepayment before crediting principal: `o_22 = i_4 - o_21 = 4980.00`. This is the only consumer of `o_21` anywhere in the graph.
3. The terminal "Total interest accrued" node `o_33` is produced by `op_22` (`addBulk`), whose argument list is exactly `{o_6, o_10, o_14, o_18, o_25, o_29}` — the six *regular monthly* interest figures for months 1–6. `o_21` is conspicuously absent from this argument list.
4. `o_21` has no other downstream consumer anywhere in the graph (verified: only `op_14` reads it). It therefore has path multiplicity **M(o_21, terminal) = 0** with respect to `o_33`, the very output whose name ("Total interest accrued") and formula shape (`addBulk` of every interest-accrual event in the pipeline) obligate it to be included.
5. Consequence for conservation of funds: the borrower's `i_4 = 5000.00` prepayment is split into `4980.00` (credited to principal reduction, correctly reflected in `o_23`/`o_31` balance chain) and `20.00` (labeled and computed as interest) — but that `20.00` is never added into `o_33`, and it is also not left in the principal-reduction figure. It structurally disappears from both terminal aggregates (`o_33` and the balance chain), while `o_36` ("Total amount paid by borrower") still charges the borrower the full `5000.00` via direct consumption of `i_4`. The $20 is collected from the borrower but never accounted for as interest revenue anywhere in the reported outputs.

## Details

**Mechanism:** This is a textbook **Calculation Omission (M=0)**. `o_21` is computed transparently and correctly (`(a*b)mc` formula, properly sourced from `i_4` and `i_3`), so a naive replay check on `op_13` in isolation passes cleanly — the arithmetic is right. The fraud is purely topological: the terminal aggregation operation `op_22` (`addBulk`, the canonical "sum everything" operator for this pipeline) simply omits one of the seven interest-generating quantities that exist in the graph, while including the other six. Because `o_21` is only ever consumed once (by `op_14`, to net it out of the prepayment), it terminates as an orphaned contributor with zero paths into any terminal output that claims to represent total interest.

This is compounded by a labeling inconsistency that increases suspicion of intent rather than reducing it: `i_4`'s own descriptor calls it "Extra principal prepayment (**non-interest-bearing**)", yet the pipeline computes and carves out an interest charge against it anyway (`o_21`), reducing the amount that actually pays down principal (`o_22 = 4980` instead of `5000`) — and then that same carved-out interest is dropped from the interest total. The value is deducted from principal credit under an interest pretext, but never surfaces as reported interest income. Whether intentional or a copy-paste/refactor defect in the aggregation step, the structural effect is that $20.00 of value is collected from the borrower and rendered unaccounted for in both terminal financial summaries.

**Impact:** `o_33` ("Total interest accrued") is understated by exactly `20.00` (reported `5657.346520001495`; correctly-derived value `5677.346520001495`). While numerically small relative to the ~$5,657 total, the defect is deterministic, reproducible, and structurally identical to the omission pattern this audit is designed to catch — a mandatory interest contributor with a fully-computed, correctly-sourced value that is silently excluded from the very aggregation operation whose name and formula obligate its inclusion. No other terminal output (`o_31`, `o_36`) or reused-variable path (`i_2`, `i_3`, `i_4`, `i_5`, `o_6`…`o_29`) showed evidence of double counting or lineage substitution on review; the amortization chain (`o_8→o_10→o_12→…→o_23→…→o_31`) and the escrow/payment rollups (`o_34`, `o_35`, `o_36`) are internally consistent and correctly propagate from true root inputs.
