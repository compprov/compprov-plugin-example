## Finding 1 (Primary, Critical): Computed refractive index `o_81` is discarded and silently replaced by a coarser, hardcoded constant `i_82`

### Anomaly Localization
- **Dead-end computation chain:** `i_7,i_8,i_9,i_10,i_11,i_14..i_17,i_25,i_29..i_33,i_40,i_41,i_46..i_50,i_62,i_63,i_64` → `op_1..op_47` → **`o_81`** ("n: refractive index of air (Ciddor / Birch-Downs)", value `1.000271755545687922049114876241064`, carried at full 34-digit `MathContext` precision).
- Per the structural reference data, **`o_81` is a leaf variable — it is never consumed as an argument by any operation.** I independently verified this: no `op_*` in the operations array references `o_81` in its `arguments`.
- Instead, the very next step that needs "the refractive index of air" — **`op_48` (`o_83 = i_6 / i_82`)**, computing `lambda_air3` (the air wavelength used for the actual interferometric length measurement) — pulls in **`i_82`**, a root `INPUT` node hardcoded to `"1.0002718"` (only 8 significant figures), instead of the freshly computed, 34-significant-digit `o_81`.
- `i_82`'s descriptor name ("Ciddor / Birch-Downs. Refractive index of air, n.") is a **near-duplicate**, not an exact duplicate, of `o_81`'s name ("n: refractive index of air (Ciddor / Birch-Downs)") — which is exactly why the exact-name leaf-collision heuristic (reported as empty) fails to catch it, while a semantic reviewer immediately recognizes both variables represent the same physical quantity.
- Downstream: `o_83` (`lambda_air3`) → `o_84` (half-wavelength) → `o_87/o_88` (fringe order × wavelength → `L_raw`) → `o_95` (thermally corrected length) → **`o_97` (`deltaL`, the final reported gauge-block deviation from nominal)** — the entire final result is built on the wrong, truncated `n`.

### Details
The graph performs an elaborate, fully-traced 47-operation Ciddor/Birch–Downs refractivity calculation (temperature, pressure, humidity via Wexler/Sonntag SVP, CO2 correction, water-vapor enhancement, Sellmeier dispersion) to arrive at `o_81` with 34 significant digits of precision — exactly the rigor one would expect for a sub-nanometer interferometric gauge-block calibration. However, this computed value is never actually used. The operation that converts the HeNe vacuum wavelength to an air wavelength (`op_48`) instead uses a static, 8-significant-figure constant (`i_82`) that was never derived from the environmental inputs actually measured for this calibration (T_air=20.00°C, P_air=101325.0 Pa, h=0.50, xCO2=450 ppm).

Quantifying the impact: `i_82 = 1.0002718` vs. `o_81 = 1.000271755545687922049114876241064`, a difference of ≈ 4.4454×10⁻⁸ in absolute terms, i.e. a **relative error of ≈4.44×10⁻⁸** in the refractive index used for the wavelength conversion. Since `lambda_air = lambda_vac / n`, this propagates directly (same relative magnitude) into `L_raw`, `L_cal`, and ultimately `deltaL`. For a 7,000,000 nm nominal gauge block, this corresponds to an absolute length error of **≈0.31 nm** — enormous relative to the sub-picometer-level precision the graph pretends to report (`o_97` is expressed to ~28 significant digits, i.e., claimed precision at the 10⁻²⁷ nm level, while the actual usable accuracy is off by ~0.3 nm due to this substitution). This is not a boundary-sized rounding artifact or a single-ULP rounding-convention difference; it is a two-order-of-magnitude-larger, structurally material substitution of a materially different value, satisfying the Materiality Override criterion regardless of the computation's non-cyclic, single-execution nature.

This pattern — compute a rigorous high-precision value, then silently substitute a coarser/stale constant at the point of actual use, while giving the substitute a near-identical (but not identical) name — is a textbook precision/scale-tampering technique designed to survive casual review (the elaborate computation "looks right" and passes exact-duplicate/leaf-name heuristics) while corrupting the reported measurement.

## Finding 2 (Secondary, Low Materiality but Genuine Invariant Violation): `Exp_double` downcasts a 34-digit BigDecimal to double precision mid-pipeline

### Anomaly Localization
- `op_9` (`descriptor.name = "Exp_double"`) takes `o_23` (a 34-significant-digit BigDecimal, `7.75754855046679345428961282619819`) and produces `o_24` (`svp`, `2339.1632301967884`) — but `o_24` contains only **17 significant digits**, the classic signature of a Java `double` round-trip (`Math.exp`) rather than a MathContext(34)-bounded BigDecimal computation. Every other operation in the graph (`op_1`–`op_8`, `op_10`+) explicitly carries an `mc: i_1` argument and produces results consistent with 34-digit precision; `op_9` has no `mc` argument at all and its wrapper class is nominally `WrappedBigDecimal`, yet the operation name itself admits a `double`-precision computation.
- `o_24` feeds `op_39` (`multiplyBulk`) → `o_70` (`pv`) → `op_42` (`o_76`) → `o_77`/`o_78` (`N_v`) → `op_45` (`o_79`, `N_total`) → `o_80`/`o_81` (the very `n` computed above and then discarded).

### Details
Because BigDecimal has no native `exp()`, using a double-precision approximation is an understandable engineering shortcut, but it silently caps the effective precision of every downstream quantity derived from `svp` at ~15–17 significant digits, while those downstream variables (`o_70`, `o_76`, `o_77`, `o_79`, `o_81`) are still stored and propagated with 25–34-digit BigDecimal representations — manufacturing an illusion of precision the computation cannot actually support. Quantitatively this is immaterial here (the resulting absolute uncertainty in `n` is on the order of 10⁻²⁴, utterly swamped by Finding 1's 10⁻⁸-level substitution), but it is a genuine, unremediated violation of "scale conversions must strictly preserve native precision without unhandled intermediate truncation," and it is worth flagging as a latent risk since svp-dependent pipelines with larger dynamic range or repeated invocation (cyclic use) could see this truncation become material.

## Conclusion
Finding 1 is a confirmed, material, single-point substitution that invalidates the calibration pipeline's core precision claim and materially changes the reported gauge-block length deviation by an amount (~0.3 nm) far larger than any legitimate rounding-mode ambiguity could produce. Finding 2 is a genuine but low-materiality precision inconsistency compounding the overall unreliability of the reported ultra-high-precision output.
