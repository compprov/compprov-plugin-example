## Anomaly Localization

**Implicated nodes:** `i_1` (MathContext, precision=16, HALF_EVEN, name="Computation precision"), `i_2` (MathContext, precision=3, DOWN, name="Computation precision" — **identical display name to `i_1`**), `op_1`, `op_3`, `op_5`, `op_7`, `op_9`, `op_11`, `op_13`, `op_14`, `op_15` (all downstream arithmetic that legitimately consumes `i_1`), and specifically `op_7` (`multiply`, Comprehensive coinsurance step, resultId `o_18`).

**Flow of the attack:**
1. Every monetary computation in this pipeline (`op_1`, `op_3`, `op_5`, `op_9`, `op_11`, `op_13`, `op_14`, `op_15`) is wired to the same global rounding context `i_1` (precision 16, HALF_EVEN) — the natural, high-fidelity "Computation precision" root input.
2. Exactly one operation, `op_7` — the multiply that computes the **Comprehensive** claim's coinsurance amount (`o_17 * i_14 -> o_18`), the single largest claim in the entire batch ($20,000 claim amount, $19,000 net-of-deductible) — is instead wired to `i_2`.
3. `i_2` is a second root `MathContext` INPUT that shares the *exact same descriptor name* ("Computation precision") as `i_1`, but silently carries a drastically different, lossy configuration: precision 3, rounding mode `DOWN` (truncate-toward-zero, i.e. it can only ever reduce a monetary result, never round it up).
4. `i_2` has no other consumer anywhere in the graph — it exists solely to be substituted into this one high-value branch.
5. In this particular execution the substitution is numerically invisible: 19000.00 × 0.90 = 17100.0000 exactly, whose significant digits ("171" + trailing zeros) survive 3-digit DOWN truncation unchanged, so `o_18` = 1.71E+4 = 17100, identical to what `i_1` would have produced. The subsequent `min(o_18, i_15)` still correctly yields `o_19` = 12000.00.

## Details

This is a textbook **Lineage Disconnection / Context Substitution** pattern (M=1, wrong source), specifically flagged by the structural reference data: `i_2` is a root `INPUT` with no producing operation that exactly mirrors a sibling's display name ("Computation precision" = `i_1`'s name), yet carries materially different semantics. Per the audit discipline, the fact that it is openly declared as a root `INPUT` with full metadata is not exculpatory — it is precisely the mechanism a disguised substitution uses to look transparent.

Why local/casual replay checks pass: each operation still deterministically replays given its own declared arguments — `op_7` correctly computes `o_17 * i_14` under `mc=i_2`, and the result is internally consistent with that (wrong) context. A naive checker validating "does each node's output match its own inputs" would find nothing wrong. Only forward-propagating from the *true* global precision root (`i_1`, which every sibling operation for Collision and Liability correctly uses) and comparing against the actual consumed context in `op_7` reveals the divergence.

Consequence / impact: because `DOWN` rounding can only truncate a positive quantity downward, this substitution constitutes a latent underpayment mechanism specific to the Comprehensive claim's coinsurance calculation — the branch with the largest dollar exposure. In this specific run the inputs happen to be "round" numbers ($19,000 × 0.90) that produce a result whose significant digits are unaffected by 3-digit truncation, so the reported terminal values (`o_19`=12000.00, `o_28`=22750.0000, `o_30`=9100.000000, `o_31`=13650.000000) are numerically unchanged from what the correct, uniform-precision computation would produce. However, the wiring itself is tampered: the coinsurance amount for the Comprehensive claim is not actually derived from the pipeline's declared/true computation-precision root, and any claim amount, deductible, or coinsurance rate combination that produces a non-trivial 4th-or-higher significant digit in that multiplication would silently under-report the coinsurance amount and, transitively, the total payout, reinsurance recovery, and net loss — without tripping any single-node replay check.

Secondary, lower-severity observation: `o_28` ("Total payout") is consumed twice en route to the terminal `o_31` ("Net loss") — once directly in `op_15` and once indirectly via `op_14`→`o_30`→`op_15`. This matches the literal shape of a Double Counting candidate (`o_28` flagged as multi-consumed in the reference data), but the formula `Net loss = Total payout − (Total payout × reinsurance rate)` is the standard, auditable net-of-reinsurance calculation and is not itself evidence of inflation/deflation fraud; it is noted here for completeness but is assessed as benign given the transparent, self-consistent formula and lack of any hidden third path.

No Calculation Omission (M=0) was found: all three claim payouts (`o_11`, `o_19`, `o_27`) are present as arguments to the `addBulk` terminal aggregation `op_13`, and the sole true leaf (`o_31`) is reached by a complete, unbroken chain from all three claim branches.
