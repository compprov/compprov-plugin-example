## Anomaly Localization

**Implicated nodes:** `i_1` (legitimate MathContext, precision=16, HALF_EVEN), `i_2` (labeled *"Computation precision (tampered)"*, precision=2, rounding=DOWN), `op_7` (multiply), `o_13` (Balance after payment [Month 2]), `o_15` (Interest accrued [Month 3]), and every downstream node that consumes `o_15`'s corrupted value: `o_16`, `o_17`, `o_19`, `o_20`, `o_21`, `o_22`, `o_24`, `o_25`, `o_26`, `o_28`, `o_29`, `o_30` (Ending balance, leaf), and `o_32` (Total interest paid, leaf).

**Attack flow:**
1. Throughout the entire six-month amortization, every `multiply`/`subtract`/`addBulk` operation consistently uses `mc = i_1` (precision 16, HALF_EVEN) — this is the graph's own established, correct computation context.
2. At `op_7` (`multiply`, resultId `o_15`, computing "Interest accrued [Month 3]"), the `mc` argument is silently swapped to `i_2` — the input node explicitly and self-admittedly named **"Computation precision (tampered)"** (precision 2, rounding DOWN).
3. The correct calculation, `o_13 (237915.84000000) * i_4 (0.004)`, evaluates to `951.66336`. Under the graph's normal `i_1` context this would round/format consistently with the surrounding decimal-place pattern (e.g., `951.66336000000`). Instead, under the substituted `i_2` context (2 significant digits, truncate-toward-zero), the result collapses to `9.5E+2` (950) — exactly reproducing the stored value, so **local deterministic replay of `op_7` in isolation passes cleanly**.
4. This corrupted `o_15` (950 instead of ~951.66336) then legitimately and correctly propagates forward: `o_16` (principal, month 3) = 2000 − 950 = 1050.00 (matches, but the correct principal should have been ~1048.33664); `o_17` (balance, month 3) = 237915.84 − 1050 = 236865.84 (matches, but correct balance should be ~236867.50336). Every subsequent month (4, 5, 6) inherits and compounds this discrepancy through the balance chain (`o_17→o_19→o_21→o_22→o_24→o_26→o_28→o_29→o_30`).
5. The two leaf/terminal outputs `o_30` ("Ending balance") and `o_32` ("Total interest paid", an `addBulk` of `o_7, o_11, o_15, o_19, o_24, o_28`) both silently inherit this corruption — they are the final reported compliance/financial figures of the pipeline, and both are materially wrong because one interior operation quietly substituted the audited, standardized precision context for a differently-labeled, degraded one.

## Details

This is a textbook **Context Substitution** rather than a value substitution: the adversary did not need to fabricate a hardcoded principal/interest figure — swapping the `MathContext` argument at a single `multiply` call is sufficient to deterministically produce a materially different (understated) interest figure while every mathematical operator, formula, and downstream consumer performs completely legitimate, verifiable arithmetic on top of that corrupted seed. A naive/local auditor who checks "does `op_7`'s formula `(a*b)mc` reproduce `o_15`'s stored value from `o_13` and `i_4`" will find that it does — the replay converges. Only a check of *which* MathContext was used, and whether that choice is consistent with the rest of the graph's own computation chain for the same quantity (interest accrual), reveals the break: every other interest/principal/balance operation in the graph uses `i_1`; only this one operation, at a materially significant midpoint of the schedule, uses `i_2` — a context whose own descriptor name ("tampered") effectively confesses its illegitimacy.

The consequence is concrete and material: Month 3 interest is understated by ~$1.66 and principal overstated by the same amount, and this delta is durably baked into every subsequent month's balance, the final "Ending balance" (`o_30`, leaf/terminal — never further reconciled against an independently-computed twin), and the "Total interest paid" (`o_32`, leaf/terminal), which directly understates total interest income/liability reported for the loan. Although the numeric drift here (~$1.66 on one step) is small in absolute terms, the mechanism — routing a live financial computation through a MathContext explicitly different from, and lower-fidelity than, the one used everywhere else in the same pipeline — is precisely the "legitimate sequence of upstream operations... then substituted at a critical downstream step with a foreign, unmonitored value" pattern the audit is designed to catch, and it would generalize to arbitrarily large drift if reused at a larger-magnitude step. There is no metadata, comment, or documented rationale anywhere in the graph justifying why `i_2` — a context the graph itself labels as tampered — is legitimately substituted for `i_1` at exactly one operation in an otherwise perfectly uniform precision regime.
