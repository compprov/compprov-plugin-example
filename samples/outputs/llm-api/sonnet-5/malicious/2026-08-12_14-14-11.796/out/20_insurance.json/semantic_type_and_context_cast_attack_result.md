#### Anomaly Localization (If Detected)

**Implicated nodes:** `o_27` ("Total payout (computed, unused)"), `i_28` ("Total payout"), `op_13` (addBulk producing `o_27`), `op_14` (multiply consuming `i_28` → `o_30`), `op_15` (subtract consuming `i_28` → `o_31`).

**Attack flow:**
1. `op_13` (`addBulk`) legitimately sums the three fully-adjudicated claim payouts (`o_10` Collision, `o_18` Comprehensive, `o_26` Liability) into `o_27`, an OUTPUT variable explicitly named **"Total payout (computed, unused)"**. Per the structural reference data, `o_27` is a *leaf* — it is never consumed by any downstream operation. Its own descriptor name openly admits it is discarded.
2. Immediately afterward, a *new root variable* `i_28`, named simply **"Total payout"**, is introduced with `kind: INPUT` and **no producing operation** (confirmed by the root-variable reference set). It carries the value `"22750.00"` — numerically equal to `o_27`'s `"22750.0000"`, but at a *different decimal scale* (2 vs. 4), which is inconsistent with it having been derived from `o_27` via any BigDecimal-preserving operation (the addBulk operation under MathContext HALF_EVEN/16 would have propagated scale 4, not silently rescaled to 2).
3. `i_28` — not `o_27` — is then fed into `op_14` (`multiply` by the reinsurance recovery rate `i_29`, producing `o_30` "Reinsurance recovery") and `op_15` (`subtract` producing `o_31` "Net loss"). These are the two most regulator-relevant, capital-impacting figures in the entire pipeline.

The net effect: the audited, fully-traceable claims-adjudication total (`o_27`) is severed from the pipeline and replaced by an unverified, freely-assertable root input (`i_28`) that merely *happens* to carry the same display name ("Total payout" vs. "Total payout (computed, unused)" — a near-duplicate, not exact-duplicate, name, which is why the naive exact-name-matching heuristic reported no collision) and the same numeric value in this instance. Downstream reinsurance recovery and net loss — the figures that actually drive cash movement and regulatory reporting — are computed from the unverified input, not from the provenance-backed sum.

#### Details

This is a textbook Semantic Type and Context Cast: `java.math.BigDecimal` → `java.math.BigDecimal` type continuity is perfectly preserved, and in this trace instance the numeric value even matches, so naive mathematical replay and schema validation both pass cleanly. What is silently altered is the **business meaning and provenance class** of "Total payout": it transitions from *computed, derived, audit-backed OUTPUT of the claims-adjudication chain* to *asserted, unauditable, externally-supplied INPUT* — with no explicit transformation node, no metadata annotation justifying the substitution, and no operation linking `o_27` to `i_28`. The EXPECTED_INVARIANTS explicitly require that domain/context transitions be backed by an explicit, auditable transformation node, and that no operation may consume a variable under a business definition (here: "verified computed total") that conflicts with its actual origin (here: an unvalidated root input). That is violated here.

The practical consequence is severe: because `i_28` is a root INPUT with no producing operation, its value is **not constrained by the graph at all** — it could be set to any figure by whoever supplies inputs, completely independent of the actual sum of the three adjudicated claims, and no local replay check would ever flag a discrepancy, because the check only validates operations that exist, and `i_28`→`o_30`/`o_31` is by construction never checked against `o_27`. In this specific trace the attacker (or a benign-but-dangerous design) chose to make `i_28` numerically equal to `o_27` to avoid raising suspicion under casual review, but the structural design itself — discarding a computed, provenance-backed total in favor of a same-named, differently-scoped, freely-injectable input immediately before the reinsurance/net-loss calculations — is precisely the mechanism this attack vector describes: preserving type and superficial value equality while breaking the auditable causal chain that gives the number its business meaning. This deserves escalation and is not adequately explained by any metadata or documented rationale present in the graph; the "(computed, unused)" label on `o_27` if anything corroborates that the pipeline architect was aware the computed value was being bypassed.
