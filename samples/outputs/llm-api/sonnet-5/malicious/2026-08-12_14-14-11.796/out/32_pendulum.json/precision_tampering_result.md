## Anomaly Localization

**Implicated nodes:**
- `i_1` — MathContext(precision=16, HALF_EVEN), descriptor name "Computation precision (DECIMAL64)" — the pipeline-standard context used by **every** operation except one.
- `i_2` — MathContext(precision=3, DOWN), descriptor name "Computation precision (tampered)" — an alternate, drastically degraded, non-default-rounding context.
- `op_2` (`sqrt`) — the **only** operation in the entire graph that consumes `mc=i_2` instead of `mc=i_1`.
- `o_9` (`sqrt(L/g)`) — result of `op_2`, value `0.451`, truncated to 3 significant figures via `DOWN` rounding.
- `op_4` (`multiply`, `mc=i_1`) — consumes the degraded `o_9` alongside the full-precision `o_10` (2π), producing `o_11`.
- `o_11` (`Period, T`) = `2.833716573537991` — presented with 16 apparent significant digits, but numerically anchored on a 3-sig-fig intermediate.
- `op_5`/`o_12` (Frequency) and `op_6`/`o_13` (Angular frequency, `2π/T`) — both downstream consumers of the corrupted `o_11`.
- `op_7`/`o_14` and `op_8`/`o_15` — an independent, correctly-computed cross-check path (`sqrt(g/L)`, entirely on `mc=i_1`) yielding `o_15 = 2.213594362117866`.

**Attack flow:** `i_3, i_4 → op_1(mc=i_1) → o_8` is computed correctly at full precision. Then `o_8 → op_2` is deliberately routed through `mc=i_2` (precision 3, rounding DOWN) instead of the standard `mc=i_1`, yielding `o_9 = 0.451` versus the true value `sqrt(10/49) ≈ 0.4517539514526256`. This truncated value is then laundered through `op_4`, a full-precision (`mc=i_1`) multiply against `o_10` (2π, computed correctly), producing `o_11 = 2.833716573537991` — a Period value that looks fully precise (16 significant digits) but is actually built on a value with only 3 correct significant digits. The true Period should be ≈`2.838454...`, a discrepancy of ≈`0.0047 s` (~0.17% relative error) — far beyond the ≤1-ULP ceiling attributable to a single legitimate rounding-convention choice. This error further propagates into `o_12` (Frequency) and `o_13` (Angular frequency = 2π/T = `2.217294900221729`).

Critically, the graph contains its own physical cross-check: for a simple pendulum, ω = 2π/T must equal sqrt(g/L). The independently-computed `o_15 = 2.213594362117866` (via the untampered `op_7`→`op_8` path, both on `mc=i_1`) does **not** match `o_13 = 2.217294900221729`. The two values, which represent the same physical quantity computed by two different but supposedly equivalent routes, diverge by ≈`0.0037` (~0.17%) — solely and directly attributable to the single swapped MathContext at `op_2`.

## Details

The mechanism exploits the fact that each operation node, viewed in isolation, replays correctly: `op_2`'s output (`0.451`) is exactly what you get applying `DOWN` rounding to 3 significant figures on the exact sqrt of `o_8`, so a naive per-node arithmetic replay check passes with zero delta. The fraud is not in violating the declared MathContext of any single operation — it's in the *choice* of MathContext itself: an attacker substituted a non-standard, severely low-precision, truncating context (`i_2`, explicitly labeled "tampered" in its own metadata) into exactly one operation in an otherwise uniformly high-precision (`i_1`, HALF_EVEN, precision 16) pipeline. Because the subsequent multiply (`op_4`) executes at full precision, the corrupted 3-significant-digit value is silently "upgraded" to display 16 digits of specious precision in the final Period output, making the tampering invisible unless the intermediate `o_9` is scrutinized against the pipeline's dominant precision convention, or unless the embedded cross-check (`o_13` vs `o_15`) is examined.

This is not merely a boundary-sized single-rounding-mode difference (which the invariants correctly exempt) — the resulting discrepancy of ~0.17% between two values that should be physically identical (`o_13` and `o_15`) is orders of magnitude larger than a single-ULP/1-unit-at-target-scale rounding artifact, and it is corroborated by an independently-computed value already present in the graph, not merely by an external recomputation. The consequence is that the reported Period (`o_11`), Frequency (`o_12`), and Angular frequency (`o_13`) — the primary physical outputs of this pipeline — are measurably and materially wrong, while superficial per-node replay and the presence of an explicit `mc` argument on `op_2` would cause an automated or casual auditor to wave it through as "just a different declared precision." The self-labeling of `i_2` as "tampered" together with the internal cross-check contradiction removes any reasonable benign interpretation (e.g., legitimate intentional truncation for display) — no metadata or rationale anywhere in the graph documents or justifies degrading precision specifically at the sqrt step feeding the headline Period output.
